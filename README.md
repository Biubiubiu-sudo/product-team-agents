# 产品需求小组智能体协同框架

> **设计理念文档** - 记录我们如何一步步设计出这个多智能体协作框架，以及每个设计决策背后的思考逻辑。

---

## 一、设计初衷

### 1.1 核心目标

- 输出**高质量、完整**的产品需求文档
- PRD 是**开发团队和测试工程师的唯一参考**
- PRD 同时也是**给客户的交付物**
- 最终使开发出来的项目成为**高质量的软件项目**

### 1.2 适用场景

- 从 0 到 1 建设新产品
- 已有产品新增需求
- 需求变更场景

### 1.3 最终输出产物

- **PRD（产品需求文档）**：完整、可执行、测试可用
- **UI 界面设计提示词**：可用于 AI 绘图工具生成原型图

---

## 二、团队架构设计

### 2.1 核心理念

- 每个小组成员有**自己的上下文窗口，互不干扰**
- 但又**互相协作，可以互相沟通**
- 支持**并行完成任务**，提高效率
- 由**产品负责人统一指挥调度**

### 2.2 团队组成（5 角色）

| 角色 | 职责 | 文件 |
| ---- | ---- | ---- |
| **产品负责人 (PO)** | 与用户沟通确认、协调团队、问题汇总、知识沉淀、整合输出 | `agents/product-owner.md` |
| **需求分析师** | 需求拆解、功能模块划分、用户故事、业务流程、业务规则挖掘 | `agents/requirement-analyst.md` |
| **PRD 文档专家** | PRD 编写、测试用例、验收标准、业务规则清单 | `agents/prd-writer.md` |
| **评审专家** | 独立审核 PRD 和原型的质量，检查完整性、一致性、可执行性 | `agents/prd-reviewer.md` |
| **UI 设计专家** | 界面设计、输出 AI 绘图提示词 | `agents/ui-designer.md` |

### 2.3 为什么需要评审专家？

- PRD 和原型**特别重要**，是唯一参考和交付物
- 需要**独立的质量把关**，避免遗漏和不一致
- 评审重点：PRD 完整性、PRD 与原型一致性、开发可执行性

---

## 三、沟通风格要求

### 3.1 核心原则

- **不附和用户**：有自己的专业判断，不迎合每一个想法
- **不拍马屁**：不说"您说得对"、"太棒了"等无意义肯定
- **可以毒舌**：犀利地指出问题，但要有建设性意见
- **专业直接负责任**：目标是高质量需求，不是让用户开心

### 3.2 主动追问机制

- 需求不清楚时**积极主动负责任地提出疑问**
- **不断追问用户**，使需求完善后再行动
- 各角色在工作中遇到的问题**汇总到负责人**
- 负责人**及时与用户沟通确认**

### 3.3 追问话术示例

- "等一下，你说的'用户'具体是指谁？"
- "这个功能的价值是什么？我没看出来。"
- "这里有个逻辑问题：A 和 B 是矛盾的，你想要哪个？"
- "这个需求听起来像是解决方案，不是问题。真正的问题是什么？"

---

## 四、知识沉淀机制

### 4.1 设计理念

- 让产品小组**不只是完成任务优秀**
- 还要**与用户的配合越来越默契**
- 对**需求的整个生命周期**进行良好管理

### 4.2 用户偏好文档 (USER_PROFILE.md)

**目的**：记录用户喜好和常见问题，避免重复踩坑

**内容**：
- 用户沟通风格偏好
- 业务关注点
- 常见问题 FAQ
- 历史决策记录
- 禁忌事项

### 4.3 项目规则文档 (PROJECT_RULES.md)

**目的**：记录项目特有规则，实现需求全生命周期管理

**内容**：
- 项目专属规则
- 术语表
- 需求历史和版本演进
- 变更记录（原因、影响、决策过程）
- 经验教训（踩过的坑、成功经验）

### 4.4 知识应用流程

1. **任务开始前**：读取知识文档，了解用户偏好和项目规则
2. **任务进行中**：按照已知的偏好和规则工作
3. **任务完成后**：更新知识文档，沉淀新的经验

## 六、设计演进历程

> 以下记录了这个框架从构思到成熟的完整演进过程，以及每个设计决策背后的思考逻辑。

### 6.1 里程碑一：初始架构搭建

**时间节点**：框架创建初期

**做了什么**：
- 创建 5 个角色的基础定义文件
- 定义每个角色的职责边界
- 设计基本的协作流程

**设计决策**：
- **为什么是 5 个角色而不是更多或更少？**
  - 产品负责人：必须有统一调度者，否则各角色各自为战
  - 需求分析师：需求拆解是专业工作，需要独立角色
  - PRD 专家：文档编写有其专业性，与需求分析是不同技能
  - UI 设计专家：界面设计需要独立的视觉思维
  - 评审专家：自己写自己审会有盲点，需要独立质量把关

### 6.2 里程碑二：架构升级 - 从角色切换到 Task 调度

**发现的问题**：
- 最初设计是 product-owner 通过 `@角色名` 方式切换身份执行任务
- 实际运行时发现：product-owner 自己在做所有事，而不是调度其他角色
- 任务是**串行执行**的，效率低下

**设计决策**：
- **为什么改用 Task 工具调度？**
  - Task 工具可以启动**独立的任务窗口**，每个子智能体有自己的上下文
  - 支持**并行执行**，多个子智能体可以同时工作
  - **职责分离更清晰**：product-owner 只负责调度，不负责执行具体任务

**如何体现**：
- product-owner 入口文件添加 `tools: ... Task`
- 工作手册中明确 Task 调用示例
- 约束条件中强调"禁止自己执行所有任务"

### 6.3 里程碑三：输出目录规范化

**发现的问题**：
- 测试时发现所有子智能体的输出都堆在 `doc/` 或 `docs/` 文件夹
- 没有按角色分类，文件混乱
- 难以追踪和管理

**设计决策**：
- **为什么要强制分目录输出？**
  - 清晰的目录结构便于定位和管理
  - 支持断点续传（知道哪个角色的工作到哪一步了）
  - 便于评审专家分类检查

**如何体现**：
- 每个子智能体入口文件明确输出目录：`requirement/`、`prd/`、`ui/`、`review/`
- 约束条件中添加"禁止输出到 doc、docs 等非指定目录"
- Task 调用示例中强调输出目录

**最终目录结构**：

### 6.4 里程碑四：进度实时追踪机制

**发现的问题**：
- 测试时发现子智能体的进度都是**最后统一更新**的
- 如果中途中断，**完全不知道进度卡在哪里**
- 失去了进度追踪的意义

**设计决策**：
- **为什么要求实时更新进度？**
  - 支持**断点续传**：中断后可以从上次进度继续
  - 对外可见：用户可以实时看到工作进展
  - 便于问题定位：知道哪一步出了问题

**如何体现**：
- 每个子智能体工作手册中新增"进度实时更新规则"
- 明确规定"完成一个任务就立即更新一次进度，禁止最后统一更新"
- `_progress.md` 格式模板

### 6.5 里程碑五：分模块输出与合并机制

**发现的问题**：
- PRD 专家把所有内容输出到同一个文件
- 文件过长时容易中断
- 没有按功能模块分开保存

**设计决策**：
- **为什么要分模块输出？**
  - 避免单文件过大导致输出中断
  - 便于增量修改（只改某个模块）
  - 便于评审（可以逐模块评审）

**如何体现**：
- PRD 专家约束"每个功能模块单独一个文件"
- UI 设计专家约束"每个页面单独一个文件"
- 最后合并为完整版

### 6.6 里程碑六：工作手册路径修复

**发现的问题**：
- 子智能体报告"工作手册暂不存在"
- 原因是路径是**相对路径** `.qoder/knowledge/xxx-guide.md`
- 子智能体被 Task 工具启动后，工作目录不在预期位置，找不到文件

**设计决策**：
- **为什么改用绝对路径？**
  - 子智能体可能在任意项目目录被调用
  - 绝对路径确保无论在哪里都能找到工作手册

**如何体现**：
- 所有子智能体入口文件中的工作手册路径改为 `~/.qoder/knowledge/xxx-guide.md`

### 6.7 里程碑七：评审专家工具权限修复

**发现的问题**：
- 评审专家说"我没有直接写文件的工具"
- 评审报告只能输出到对话中，无法保存为文件

**设计决策**：
- **为什么评审专家需要 Write 工具？**
  - 评审报告需要保存为文件，便于追溯
  - 支持版本化评审（v1、v2、v3...）

**如何体现**：
- prd-reviewer 入口文件 tools 字段添加 `Write`

### 6.8 里程碑八：不限次数追问机制

**发现的问题**：
- product-owner 开始工作时只主动追问一次
- 不确定是否追问清楚了

**设计决策**：
- **为什么要不限次数追问？**
  - 需求澄清是最重要的环节，宁可多问也不能带着疑问开工
  - 每个用户的表达习惯不同，有些需求需要多轮确认

**如何体现**：
- 工作原则改为"不限次数追问：需求不清楚绝不开工，一直追问到完全理解为止"
- 阶段一标题改为"阶段一：需求澄清（不限次数追问）"
- 新增"追问结束标准"（必须全部满足才能进入下一阶段）

### 6.9 里程碑九：需求分析确认机制

**发现的问题**：
- 需求分析师分析完直接交给 PRD 和 UI
- 如果分析有问题，后续工作都白费

**设计决策**：
- **为什么需求分析完要先确认再交付？**
  - 需求分析是后续所有工作的基础
  - 如果基础有问题，PRD 和 UI 都会有问题
  - 及早发现问题，避免返工

**如何体现**：
- 需求分析师工作手册新增"分析-确认-输出 循环机制"
- 有待确认问题先上报用户，确认后再更新分析
- 所有问题确认清楚后，才能交付给 PRD 和 UI

### 6.10 里程碑十：评审后修复调度机制

**发现的问题**：
- 评审发现问题后，product-owner 自己去修复
- 应该由**对应的子智能体**来修复各自的问题

**设计决策**：
- **为什么修复工作要交给子智能体？**
  - 职责分离：谁产出的文档，谁负责修复
  - 专业性：PRD 问题由 PRD 专家修复，UI 问题由 UI 专家修复
  - product-owner 只负责调度，不负责具体执行

**如何体现**：
- 核心原则"产品负责人只负责协调调度，问题修复由对应的子智能体完成"
- 新增问题修复 Task 调用示例
- 修复完成后再次调用评审专家审核修复结果

### 6.11 里程碑十一：评审专家前置理解机制

**发现的问题**：
- 评审专家直接看 PRD 和 UI，不了解原始需求
- 可能会误判（不知道某个设计是基于什么需求）

**设计决策**：
- **为什么评审前要先理解需求分析结果？**
  - 评审要有参照物，需求分析结果就是参照物
  - 检查 PRD 和 UI 是否完整覆盖需求
  - 避免脱离需求的"空评审"

**如何体现**：
- 评审专家入口文件新增"评审前置条件"
- 要求先读取需求分析文档，理解后再评审
- 评审态度新增"客观真实"、"不放过问题"、"不吹毛求疵"

### 6.12 里程碑十二：需求分析闭环确认机制

**发现的问题**：
- 需求分析师分析完直接交给 PRD 和 UI
- 如果分析有遗漏或待确认问题，后续工作质量无法保障
- 需求分析是所有后续工作的基础，必须确保质量

**设计决策**：
- **为什么需要闭环确认？**
  - 需求分析是后续所有工作的**唯一输入**
  - 需求分析有问题 → PRD 有问题 → UI 有问题 → 返工成本巨大
  - 必须在源头确保质量，而不是后期补救

- **为什么不限次数循环？**
  - 每个需求的复杂度不同，有些需要多轮澄清
  - 宁可多确认几轮，也不能带着疑问往下走

- **为什么用户说"先忽略"要记录？**
  - 这些问题不是消失了，只是暂时搁置
  - 记录到 PROJECT_RULES.md "待解决问题"中
  - 后续有时间再回来解决，不会遗忘

**如何体现**：
- 需求分析师入口文件新增"问题上报与补充分析机制"
- 需求分析师返回格式包含"状态：需要澄清/分析完成"
- 产品负责人工作手册新增"阶段二：需求分析闭环确认"完整流程
- 补充分析 Task 调用示例
- PROJECT_RULES.md 新增"待解决问题"记录格式

**闭环流程**：
```text
Task(需求分析师) 第一轮分析
        │
        ▼
   检查返回状态
   ┌────┴────┐
分析完成   需要澄清
   │         │
   │    与用户确认
   │    ┌────┴────┐
   │  用户澄清  用户说先忽略
   │    │         │
   │    │    记录到待解决问题
   │    ▼         │
   │  Task(需求分析师)
   │  补充分析
   │    │         │
   │ 还有问题？    │
   │  │是→继续循环 │
   │  │否         │
   └──┴─────┬────┘
            ▼
      进入下一阶段
```

### 6.13 里程碑十三：强规则系统

**发现的问题**：
- 智能体有时会自行更改输出目录结构
- 完整版文档内容太多时，手动输出会导致卡死
- PRD 专家有时把多个功能模块合并到一个文件

**设计决策**：
- **为什么要固定目录结构？**
  - 确保输出一致性，便于后续处理
  - 支持断点续传，知道哪个文件完成了哪个没完成
  - 便于评审专家检查

- **为什么建议用 shell 命令合并？**
  - 一次性输出大文档会占用大量上下文，导致卡死
  - shell `cat` 命令简单高效，不占用 AI 上下文
  - 分片生成 + shell 合并 = 完美方案

- **为什么 PRD 每个功能模块单独文件？**
  - 便于增量修改，只改某个模块
  - 便于评审，可以逐模块审核
  - 避免单文件过大

- **为什么 UI 每个页面单独文件？**
  - 同上，便于增量修改和评审

**如何体现**：
- 所有子智能体入口文件“必须做”和“禁止做”中强调
- 使用 `**加粗**` 突出强规则
- 工作手册中提供 shell 合并命令示例

**强规则清单**：
| 规则 | 说明 |
| ---- | ---- |
| 固定目录结构 | 禁止更改文件名、文件数量、命名规则 |
| PRD 分模块 | 每个功能模块单独一个文件 `04-功能模块-[模块名].md` |
| UI 分页面 | 每个页面单独一个文件 `XX-页面-[页面名].md` |
| shell 合并 | 完整版/汇总版必须用 `cat` 命令合并，禁止手动输出 |

### 6.14 里程碑十四：工具权限修复

**发现的问题**：
- 要求子智能体用 shell 命令合并，但 tools 中没有 Bash
- 智能体无法执行 shell 命令，导致强规则失效

**设计决策**：
- **为什么要给子智能体添加 Bash 工具？**
  - shell 合并是强规则，必须有执行能力
  - 工具权限要与工作要求匹配

**如何体现**：
- requirement-analyst: `tools: Read, Write, Grep, Glob, Bash`
- prd-writer: `tools: Read, Write, Grep, Glob, Bash`
- ui-designer: `tools: Read, Write, Grep, Glob, Bash`
- prd-reviewer: `tools: Read, Write, Grep, Glob`（不需要 Bash）
- product-owner: `tools: Read, Write, Grep, Glob, Bash, Task`

### 6.15 里程碑十五：返回格式统一

**发现的问题**：
- 之前只有需求分析师有返回格式
- PRD 专家、UI 设计师、评审专家缺少统一的返回格式
- product-owner 无法统一处理子智能体的返回

**设计决策**：
- **为什么要统一返回格式？**
  - 便于 product-owner 统一处理
  - 知道子智能体的状态（完成/需要澄清）
  - 支持闭环确认机制

**如何体现**：
- 所有子智能体都有“返回格式”章节
- 统一包含：状态 + 已完成文件 + 待澄清问题

## 九、设计原则清单

以下是本框架遵循的核心设计原则，也是我们在迭代过程中逐步提炼出来的：

1. **职责分离**：每个角色只做自己的事，product-owner 只调度不执行
2. **上下文独立**：每个子智能体有自己的任务窗口，互不干扰
3. **实时可见**：进度实时更新，随时知道工作到哪一步了
4. **断点续传**：中断后可以从上次进度继续，不丢失工作成果
5. **闭环评审**：评审发现问题 → 调度修复 → 再次评审 → 直到通过
6. **确认优先**：有疑问先确认，宁可多问也不猜测
7. **知识沉淀**：每次协作都让系统更了解用户和项目
